# Content model — LangExtract docs

The content model the site is actually built on. It defines the *types* of pages
the site holds, the rules each type follows, and how a reader moves between them.
It is designed to grow: new pages slot into an existing type and an existing
place in the journey, so adding them later needs no restructuring.

This supersedes the earlier `source-material/content-model-DRAFT.md` (kept as the
historical first-pass record). Approved by John on 2026-06-21; expanded the same
day from the first four-page slice to a full Concepts + How-to + Reference site.

## The model: four content types (Diátaxis-aligned)

Every page maps to exactly one type. This keeps a reference page from drifting
into a tutorial and forces each gap in the README to become its own page.

| Type | Orientation | Answers | Rules |
|---|---|---|---|
| **Tutorial** | Learning | "Get me a first win." | One happy path, minimal choices, every snippet runs as written, ends with a working artifact. |
| **Concept** | Understanding | "How does this work, and why?" | Builds the mental model; no copy-paste task; hands off to how-to/reference for "now do it." |
| **How-to** | Task | "How do I do X?" | Assumes the basics; one goal per page; shows the minimal change from the quickstart. |
| **Reference** | Information | "What exactly does this do?" | Dry, complete, accurate; signatures/types/defaults/raises; traceable to source (`file:line`). |

**Why four types, not a flat "Guides + API" split:** the upstream README mixes
"learn it," "understand it," and "look it up" in one scroll, so new users get a
good first five minutes and then fall off a cliff. A typed model gives each of
those jobs its own home.

## How the types relate

```
Tutorial (Quickstart) ──"now understand why"──▶ Concept pages
     │                                              │
     │ "ready for a real task"                      │ "do this specific thing"
     ▼                                              ▼
  How-to recipes ◀───────"look up exact args"──── Reference (API)
```

- **Tutorial** is the only page that assumes zero knowledge; everything links
  back to it as the prerequisite.
- **Concept** pages never tell you to run something — they hand off.
- **Reference** is the leaf: many pages link in; it links out only to sibling
  reference entries.

## The reader journey (and the nav order built on it)

A reader arrives in one of these states; the sidebar order follows the arc:

> **"What is this?"** → **"How do I start?"** → **"How does it work / how do I build?"** → **"What exactly does this function do?"**

Reference sits near the end — out of a newcomer's way, one click from anyone who
knows what they want.

## How the model maps to the file tree and sidebar

The sidebar is **autogenerated** from the `docs/` folder structure plus
`sidebar_position` front matter and `_category_.json` files — so the file layout
*is* the IA. Adding a page is: drop a Markdown file in the right folder with a
`sidebar_position`, and it appears in journey order.

```
docs-site/docs/
├─ intro.md                          # Introduction (sidebar_position: 1)
├─ quickstart.md                     # Quickstart (sidebar_position: 2)
├─ concepts/                         # "Concepts" category (position 3)
│   ├─ _category_.json
│   ├─ how-extraction-works.md       # (position 1)
│   ├─ grounding.md                  # (position 2)
│   └─ model-backends.md             # (position 3)
├─ how-to/                           # "How-to guides" category (position 4)
│   ├─ _category_.json
│   ├─ long-document-workflow.md     # (position 1)
│   ├─ use-openai.md                 # (position 2)
│   ├─ use-ollama.md                 # (position 3)
│   ├─ write-prompts-and-examples.md # (position 4)
│   ├─ work-with-results.md          # (position 5)
│   └─ api-keys.md                   # (position 6)
└─ reference/                        # "Reference" category (position 5)
    ├─ _category_.json
    └─ api.md
```

## Where it grows next (no rework required)

- **More how-to guides:** add a page under `docs/how-to/` (for example
  "Write a custom provider") — it slots into the existing How-to category with a
  `sidebar_position`.
- **Troubleshooting:** a single cross-cutting how-to page, linked from the
  concept and reference pages where the relevant errors surface.
- **Deeper reference:** split `reference/api.md` into per-area pages
  (providers, tokenizer, resolver, chunking) once it outgrows one page.

## Fixed constraints (apply to every page)

- LangExtract is **not an officially supported Google product**; the site never
  presents itself as official Google documentation.
- Every technical claim is grounded in the v1.5.0 source; no invented parameters
  or behavior.
- Voice: clear, professional product-documentation tone — direct and concrete,
  no marketing language.
- Style: the prose follows the
  [Google developer documentation style guide](https://developers.google.com/style)
  — second person, present tense, active voice, sentence-case headings, and
  descriptive link text. Prose uses no em dashes; replace each with a colon,
  comma, or parentheses by role.
